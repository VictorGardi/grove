# Plan: agent profiles and the `auto` flow

Two repos change: **skills** (`~/git/grove-skills`: new skills, shared references, validate script) and **app** (`~/git/grove`: `auto` stages in `resources/workflow.yaml`, `grove new --model`). Nothing in the app learns what a "run" is.

## Decisions

### D1. Profile schema in `grove.config.json`

**Context.** The human changes which agent and model plays each role by editing config and passing `--profile`. The shape must not block OpenCode later, and the app must keep ignoring it (it reads only `artifactRoot`).

**Options.**
- A. Top-level keys in `grove.config.json`: `"profile": "default"` and `"profiles": { "<name>": { "<role>": { "agent": "claude", "model": "<alias>" } } }`. Pro: where the outcome puts it, per-repo, travels with the repo, no new file or loader. Con: the skills schema (`additionalProperties: false`) needs two new keys.
- B. A separate `grove.profiles.json`. Pro: no schema edit. Con: a second config file, a second watcher/location to learn; outcome says `grove.config.json`.
- C. Role → model string only. Pro: shortest. Con: blocks OpenCode (no `agent`) and needs a breaking change later.

**Pick: A.** Rules: the five roles are `cto researcher planner reviewer implementer`, all optional per profile. A missing role, a missing `profiles`, or no active profile means "inherit": no model is passed and the agent runs with the session's own. With no active profile the profile name used in branch names and `04-run.md` is `inherit`. `--profile X` overrides `profile`; an unknown profile name stops the skill. `agent` must be `claude` in v1, anything else stops the skill with "not supported yet". `model` is a model alias, because the same value goes to both the Agent tool's `model` param and `claude --model`. No fallback across profiles (a role missing in `cheap` does not read `default`): one predictable rule.
**Outcome impact:** gives the "edit profiles, pick with `--profile`" behaviour. The schema edit is in `shared/config.schema.json` only; no app code.

### D2. Skills name roles only; `grove new --model` carries the session model

**Context.** Workflow/skills say what and when with role names; profiles say who. Skills must never name models. Subagents get their model per call; the child *session* needs a model at launch.

**Options.**
- A. One shared reference `roles.md` defines the five roles and the resolution rule (D1); skills say "spawn the `researcher` subagent" and pass the resolved `model` on the Agent call (omitted when inherited). The child session main agent is the `planner` role and is launched with a new `grove new --model <m>`. A validate check bans model aliases in the auto skills. Pro: one place, mechanically enforced. Con: a small app change (below).
- B. Generate `.claude/agents/<role>.md` files with a model each. Pro: no app change. Con: generated files to keep in sync; the outcome rules it out.
- C. Pass the model to the child through an env var or by typing `/model` into the session. Pro: no argv change. Con: invisible, racy (`/model` is typed text), not recorded in the session, lost on resume.

**Pick: A.** App change, end to end: `src/cli/args.ts` (+`USAGE`, `--model` only with `claude`; other kinds are a usage error), `src/cli/index.ts`, `src/shared/cli.ts` (additive param, no protocol bump per ADR 0027), `src/main/cliServer.ts`, `core.sessionCreate`, `AgentSource.argv` opts `{model}`, `claudeArgv` (`--model <m>` on start and on resume), and one optional persisted `Session.launchModel` so a resumed session keeps its model (an optional field with no default needs no state migration; `seenAt` is the precedent; `Session.model` stays the live display field). The planner role also covers `grove-auto`'s own session: it keeps whatever model the human started it with (no self-relaunch); the CTO, researcher and reviewer subagents get theirs from the profile.
**Outcome impact:** "changing a profile changes which agents and models are used" for subagents and child sessions, and the model is in the session record.

### D3. Where a run keeps its slices and state

**Context.** `grove-run` must find slices, know which are done, and survive a halt or a new parent session, across a parent and one child per slice, with one worktree and one commit per slice. The outcome wants `04-run.md` to record profile, models, per-slice plan, commit, verdict, fix rounds, deviations, and wants two runs of one ticket to be comparable.

**Options.**
- A. `04-run.md` lives in the run's **worktree**, committed with each slice's commit. The parent reads it by absolute path. Slices come from `### Slice N — <outcome>` headings in `03-plan.md`; a slice is done when `04-run.md` has `## Slice N` with `Status: done` and a `Commit:` sha. Next slice = first not done. Pro: state is on the branch, so each run (branch) has its own log, and re-running with another profile leaves two comparable files; children write inside their own cwd (no outside-cwd permission prompts); the app already shows a worktree's copy as its own project and a chip. Con: the feature card in the main checkout does not show run progress; the final approval must run in the worktree (D6).
- B. `04-run.md` in the main checkout, written by the parent only. Pro: the card follows the run. Con: children would need to write outside their cwd or report through `grove read` (lossy); a second run overwrites the first.
- C. A JSON state file next to the skill's working data. Con: a new format and a second source of truth beside the markdown the human reads.

**Pick: A.** One run = one branch `run/<slug>-<profile>` (suffix `-2`, `-3` on collision) = one worktree. The first child creates it (`grove new claude --child --worktree --branch <b> --base <plan-commit> --label <label> --model <planner> --prompt …`), where `<plan-commit>` is the commit that holds the approved bundle (`git log -1 --format=%H -- docs/work/<slug>/03-plan.md`), not HEAD: a second run of the same ticket after the first was merged still starts from the plan, with no earlier `04-run.md` and none of the first run's code, so two runs compare cleanly. `--base` is the uncommitted worktree work noted in Slice 5's precondition; it must be committed before Slice 1. later children use `--cwd <worktree>`. The parent finds the path with `git worktree list --porcelain`. Precondition: `grove-run` requires the plan bundle approved and `docs/work/<slug>/` committed; if not, it asks (question tool) to commit it as `<slug>: approved plan`. The slice-1 child writes the `04-run.md` header (profile name, roles with the model requested for each, branch); every child appends its slice section: its session label, the detailed slice plan, commit, reviewer verdict, fix rounds, deviations, models passed to its subagents. Commit format `<slug>: slice N — <outcome>`.
**Outcome impact:** items 6–8 and 12 of the walkthrough; `04-run.md` records the models that were *requested* (the harness does not report back a subagent's actual model).

### D4. Halts, review gates and `--continue`

**Context.** Slices 2..N run unattended; failures and permission prompts must stop the run without starting later slices; the human resumes after choosing.

**Options.**
- A. The parent starts each child with `grove new claude --child --label <branch>-slice-<n>-a<k> … --wait --timeout 540` and, on exit 124, loops `grove wait <label> --timeout 540` (`k` = 1 + the number of sessions in `grove ls --all --json` whose label starts with `<branch>-slice-<n>-a`, so a label is never reused: a killed session is only gone, still resolvable, and a repeated label would be `ambiguous`; on a 124 `new --wait` prints no id, so the label is the handle, and the child records it in its slice section). Every `grove new --wait`, `grove wait` and `grove send --wait` call is made with the Bash tool's `timeout: 600000` (the default 120 s would kill the wait). 124 is never a halt, a slice may take as long as it takes, and the parent stays `working` for the whole unattended run. The parent stops only on exit 4 (permission/question pending in the child), 5 (child ended), or a halt. Completion is read from git, not the screen: after exit 0, `git -C <worktree> log -1 --format=%s` is `<slug>: slice N — <outcome>` (done) or `<slug>: slice N halted` (halted; the commit holds only the `04-run.md` note with `Status: halted` and `### Options`); exit 0 with neither subject first gets one nudge, `grove send <label> "Finish slice N: commit it, or write the halt note" --wait` (same 124 loop), and only if git still shows neither is it a halt ("child ended its turn without finishing"). Slice mode also says: never end the turn while a subagent is outstanding; await every subagent, and end only after the slice commit or the halt commit. Only on a halt or review gate does the parent read `04-run.md`, with `git -C <worktree> show HEAD:docs/work/<slug>/04-run.md` (no file read outside its cwd). The parent `grove kill`s a finished child only after that slice's gate (if any) is answered, so a "fix" always has a live target and a healthy run does not pile up unseen `waiting` sessions; a halted child is killed before its replacement starts. The stop is the parent's final message, one line naming the file by its worktree path ("Halted at slice 3: options in <worktree>/docs/work/<slug>/04-run.md"; for exit 4, "Stopped at slice 3: a prompt is waiting in <label>"); the sidebar shows the parent as `waiting` (the app has no message field and none is added; the one-line message is the last line in the parent's session). Children never ask the human: unsure means halt, because a question in a child is exit 4. Pro: only existing CLI behaviour, no app orchestration, state in git and one file. Con: the parent's session is busy for the whole run; unattended slices also need permissions (permissions paragraph).
- B. The child pings the parent with `grove send`. Con: needs the parent idle, adds a second channel beside exit codes.
- C. An app-side watcher that starts the next child. Rejected by the outcome.

**Pick: A.** Child rules (never ask the human): after its slice plan, delegate to `implementer` subagents, then `reviewer` (slice mode) reviews the diff against the slice plan and the plan's Decisions; blocking findings get up to **2 fix rounds**. If still failing, or a fix would change a Decision or the outcome, the child writes `Status: halted`, its session label and `### Options` (each with pros/cons and `Changes design or outcome: yes|no`), commits only the `04-run.md` note (subject `<slug>: slice N halted`), leaves the failing code uncommitted in the worktree, and ends its turn. `--continue`: pick the run by `--profile` (or, if several branches have a not-done slice, ask which with the question tool), then take the first slice not done. If its child session is still live (exit 4 case) → just `grove wait` on it (the human answered the prompt in that session). If `halted` → read the options, ask the human with the question tool (one question, options from the file); an option marked `Changes design or outcome: yes` is refused with "revise the plan first: `grove-auto <slug>`"; otherwise (if the human already named an option in this session, it is recorded without asking again) pass the choice in the fresh child's prompt (the parent never edits files in the worktree) and have that child record it as `Decision:` in the slice section. The fresh child first runs `git reset --soft HEAD~1` when HEAD is the `<slug>: slice N halted` commit, so slice N still ends as exactly one commit that contains the note, then applies the choice on top of the worktree as it stands (the option may say to reset). `--continue` also kills a leftover idle child of slice N first (the exit-4 case where the human already answered), and in that case re-derives "first slice not done" from git. Review gates: after slice 1 (always), and after every slice with `--review-each`: the parent shows a summary (built, verdict, deviations, how to see the diff: the worktree project's diff in the app) and asks continue / fix with a comment / stop. "Fix" = `grove send <child> "<comment>" --wait` (same 124 loop) to the still-live slice child, then ask again. A fix amends that slice's commit (one commit per slice stays true). Final review after the last slice, same options.
**Amendment (v5, the human's decision, 2026-10-15): the child reports back; the parent does not watch.** This supersedes option A's start-and-wait mechanics (and option B's rejection). The parent starts each child with `grove new claude --child … --label <branch>-slice-<n>-a<k>` **without `--wait`** and passes its own id (`GROVE_SESSION_ID`) in the child's prompt, then ends its turn; it runs no `grove wait` loop and no exit-124 handling. The child's last action is `grove send <parent-id> "SLICE n: done|halted — <one line>"`, sent only after the slice commit (or the halt commit) exists. The parent wakes on that message, confirms completion from git (the HEAD subject rules above are unchanged, and git, not the message, is the source of truth), then runs the review gate or starts the next child, and ends its turn again. Silence rule: a child that never reports (crash, or a permission prompt, which leaves it `waiting` in the sidebar) is seen by the human in the sidebar; the parent's last message names the child's label, and the human says "continue" in the parent session, which checks git and `grove ls` before acting. The exit-4/5 stop paths are replaced by this rule; the human-facing outcomes (a permission prompt stops the run, no later slice starts) are unchanged because the next child only starts on a report. Children still never ask the human. Slice-mode skills, Slice 1 verification (parent ends its turn after starting a child; the child's `grove send` appears in the parent), and Slices 6 and 7 follow this.

**Abandoning a run.** The human says so in the parent session; the parent asks nothing destructive: it leaves the run's branch and worktree in place and prints the removal commands (`git worktree remove <path>`, `git branch -D <branch>`), running them only if the human picks that in a question-tool question. An abandoned run is never resumed because `--continue` is explicit and picks a run by `--profile` or by asking. To re-plan, the human runs `grove-auto <slug>` (revise mode; editing an approved artifact makes it `draft` per the contract), re-approves with `grove-approve <slug> plan`, and `grove-run` starts a new run on a new branch (`-2`) from the new plan commit.

**Permissions for unattended slices (part of this decision).** The parent also needs Bash permission for `grove new|wait|send|kill|ls|read` and `git -C <worktree> …`; the slice-1 gate summary lists these command prefixes so the human can allow them ("don't ask again") before answering continue, otherwise the first-use prompt would stall slices 2..N silently. A child that hits a permission prompt is exit 4 and stops the run, as the outcome wants. But `claudeArgv` passes no permission mode, `.claude/settings.local.json` is git-ignored (absent from a fresh worktree) and a fresh worktree has no `node_modules`. Options: (a) no new mechanism, the run uses the human's own Claude permission settings (user settings or a committed `.claude/settings.json`); `grove-run` states this prerequisite in its slice-1 gate summary and on an exit-4 stop, and the slice-1 child installs dependencies if the worktree lacks them using the project's documented install command (README, `AGENTS.md`, manifest), halting if it cannot tell; (b) `grove new --permission-mode <m>` with `acceptEdits`: zero setup, but a skill silently lowers the human's permission posture and shell commands still prompt; (c) a precondition that inspects settings files: cannot see every source. **Pick (a)**; the human is told plainly that a repo without pre-approved edits halts at the first prompt. Slice 6 verifies on a repo whose settings pre-allow edits and `commands.*`.
**Outcome impact:** items 7–10 of the walkthrough and all halt/permission statements in "How I'll know it works".

### D5. The `auto` flow in `resources/workflow.yaml`

**Context.** An `auto` feature must be discovered with no card warnings (an unknown `flow:` value today warns `flow?` and falls back to `full`). A stage has one artifact and ids are global (no per-flow artifact override); `full` and `standard` are `stages: all`, so any new global stage would leak into them.

**Options.**
- A. Add three new global stages (`outcome` → `01-outcome.md`, `plan` → `03-plan.md`, `run` → `04-run.md`, each `complete_when: status approved`), place them so the global order is `questions, outcome, research, plan, run, design, structure, implementation` (the legacy five keep their relative order), make `full` and `standard` explicit five-stage lists, add `auto: { stages: [outcome, research, plan, run] }`. `research` is shared (same `02-research.md`). No code change. Pro: pure yaml, matches ADR 0002 ("a different workflow is a yaml change"); existing flows keep exactly their stages. Con: the explicit lists must be updated if someone later adds a global stage.
- B. Reuse `questions/design/structure/implementation` ids. Con: impossible, artifact names differ and one stage has one artifact.
- C. Teach the parser per-flow artifact overrides. Con: engine change for no user value.

**Pick: A.** `actions`/`stage_actions` stay as they are (inert, never interpreted). The Features board draws one column per global stage, so new stages would add empty columns to every project; Slice 3 makes it draw only the stages some feature in the project uses, so a legacy-only project looks as before. Tests: bundled yaml still parses; `full`/`standard` derive five stages as before; an `auto` feature derives four stages and no warnings; existing derive/feature tests unchanged.
**Outcome impact:** "an `auto` feature is still discovered without card warnings; existing flows unchanged".

### D6. One approval for the plan bundle, one for the run

**Context.** Only `grove-approve`, invoked by the human, approves. The outcome has two approval points: the plan bundle before the run, and the finished run.

**Options.**
- A. Two new units in the shared approval procedure: `plan` (= `01-outcome.md` + `02-research.md` + `03-plan.md`, atomic, both-or-none, like `design+structure`) and `run` (= `04-run.md`). `grove-auto` and `grove-run` never approve inline; each ends by naming the command. Content gates for `plan`: outcome has its required sections; every decision has a pick and options; decisions ≤ `limits.maxOneWayDecisions`, slices ≤ `limits.maxSlices`, each slice has verification, and slice 1 is a thin end-to-end slice; empty `## Open questions` in all three; no placeholder markers (the two literal words banned by the contract); a decision flagged "agents disagree" must carry the human's recorded pick. For `run`: every slice in `03-plan.md` has a `## Slice N` with `Status: done`, none `halted`, and a final summary section. Staleness: `grove-run` stops when `03-plan.md`'s version is newer than `04-run.md`'s `based_on`; neither unit marks anything stale itself (a run's `04-run.md` exists only in its worktree). The prompt is asked with the question tool (options "Approve now" / "Not yet"; the literal `Approve now? (yes / not yet)` stays in the question text).
- B. Reuse existing units (`questions+research`, `design+structure`, `implementation`). Con: wrong files and wrong gates for this flow.
- C. Let `grove-run` start without approval if the human says "go". Con: breaks "nothing is approved without me invoking `grove-approve`" and the hard gate.

**Pick: A.** `grove-run` has a hard gate on the `plan` unit being approved and on staleness (`based_on` versions), `--force <reason>` allowed and recorded like other gates. Because `04-run.md` lives in the worktree (D3), `grove-approve <slug> run` is run by the human in a session whose cwd is that worktree; `grove-run`'s last message prints the exact command and the worktree path (no spawned approval session: `grove-approve` is `disable-model-invocation`). Approve does not commit, so the message also says to commit the approved `04-run.md` on the run branch (`<slug>: approve run`) and then merge or open a PR; `## Final summary` holds the PR description (as `grove-implement` does). The human review of plan **decisions** line by line happens in `grove-auto`'s last step: first it prints every decision in full (context, options with pros/cons and outcome impact, the pick) and the slices; each item flagged "agents disagree" is then asked as its own question-tool question with both sides' options and pros/cons; then a question lists the decisions (pages of three) asking which to veto; a vetoed decision is re-asked with its options, the planner revises in revise mode, and the human then runs `grove-approve <slug> plan`.
**Outcome impact:** items 5 and 11 and "one `grove-approve` covers the whole plan".

### D7. The question-tool rule, and how a subagent CTO can "ask"

**Context.** Every skill in the flow must have agents ask the human through `AskUserQuestion`, one question at a time. Subagents cannot reach the human, yet the CTO is a subagent. At the time of planning the skills repo has **uncommitted edits by someone else** that add exactly this rule to every existing skill (a `## Rules` bullet: "Ask the human only through the question tool (`AskUserQuestion` in Claude …), one question at a time, with the background and your recommendation; never as plain chat text. This includes approval prompts") and a rule 9 "Asking the human" in one copy of `contract.md` (not yet in `shared/contract.md`, so `validate.sh` can fail on sync).

**Options.**
- A. Build on that rule instead of a new reference: it lives in `shared/contract.md` (rule 9, reaches every skill via `*`) plus the same `## Rules` bullet in `grove-auto` and `grove-run`; `shared/approve.md` says that in the `auto` flow the prompt is a question-tool question with options "Approve now" / "Not yet" (the literal `Approve now? (yes / not yet)` stays in the question text). Every subagent prompt template ends "you cannot reach the human; return findings, never ask", and children in slice mode never ask (D4). `validate.sh` checks that every skill contains `AskUserQuestion`. The CTO is **stateless per round**: the planner gives a fresh CTO subagent the ticket, the researchers' code map and the Q&A so far (kept in `01-outcome.md` under `## Interview log`, so nothing lives only in chat); the CTO prompt allows outcome questions only (what the human sees or does, scope, non-goals, how they will know it works; never technical choices) and the CTO returns either the next question (background, 2–4 options with outcome impact, recommendation) or the finished Outcome Brief; the planner asks the human verbatim through the tool, logs the answer, repeats (soft cap 8 questions, then play-back). The play-back is a question-tool question too (confirm / correct). Pro: one rule, one source, consistent with the in-flight work, enforceable by grep; no resumable-subagent dependency. Con: the planner is a relay.
- B. A new `shared/asking.md` copied into the three auto skills only. Con: a second source of the same rule next to the in-flight one; drift.
- C. Let the CTO subagent ask directly. Impossible: no channel to the human.

**Pick: A.** Dependency: the in-flight edits must be committed (and `shared/contract.md` made the source of rule 9, then `sync-shared.sh`) before Slice 1 lands. If their owner decides otherwise, Slice 1 adds the rule to `shared/contract.md` itself. The planner's own outcome ambiguities use the same tool and format.
**Outcome impact:** "asked only outcome questions, one at a time, with background, options, recommendation" and "in every step of the flow, through the question tool".

### D8. Packaging: two skills, shared references, one `grove-run` for both modes

**Context.** New behaviour must be reviewable, installable and linted with the least new surface.

**Options.**
- A. Two skills in `~/git/grove-skills` (not `~/git/victor/skills`, which only symlinks to it): `grove-auto` (planning) and `grove-run` (parent mode by default; child mode with `--slice N`, in `references/slice-mode.md`; the parent's child prompt is "Load the grove-run skill … Arguments: <slug> --slice N --profile P"). Shared additions: `roles.md` (MANIFEST line `roles.md grove-auto grove-run`), an additive `auto` flow section in `contract.md`/`gates.md`/`approve.md` (these sync into every skill). Plus `commands/` wrappers, README rows, `validate.sh` (new checks: `AskUserQuestion` present in every skill, no model aliases (`opus|sonnet|haiku|fable`, whole words) anywhere under `skills/grove-auto` and `skills/grove-run`, so `roles.md` and examples use `<alias>`, and `flow` may be `auto` in fixtures) and one fixture. Pro: the outcome's two skills; parent and child share one contract so they cannot drift. Con: `grove-run` is a two-mode file.
- B. Separate `grove-run-slice` skill. Pro: each file simpler. Con: a third skill, duplicated contract, the outcome lists two.
- C. Put everything in `grove-implement`. Con: it is gated on the legacy flows and structure; entangling would risk the existing flows.

**Pick: A.** The string `grove-plan` is banned by validate; the new plan file is `03-plan.md` and no skill is named that. The new symlinks appear in `~/.claude/skills` after `install.sh` (that directory is the user's `victor/skills`; they will see two new symlinks there).
**Outcome impact:** "Where changes land" list in the outcome.

## Slices

Each slice leaves `bash scripts/validate.sh` (skills repo) and `npm test && npm run typecheck` (grove repo, only slices that touch it) green. The skills repo has no `npm`; "validate" means `commands.lint` there.

### Slice 1. Thin end-to-end: outcome → plan → approve → run, happy path, on a toy ticket

**Outcome.** A human can run the whole path once on a trivial ticket in a scratch repo: `grove-auto` asks outcome questions through the question tool, writes a confirmed brief and a small plan, `grove-approve <slug> plan` approves the bundle, `grove-run <slug>` runs 2 slices in one worktree with one commit each and `04-run.md`. Deliberately missing: reviewer loop, CTO final check, profiles/models, subagents, fix rounds, halts, `--continue`, `--review-each`, the workflow.yaml stage, the `run` unit.
**Files (skills repo).** `skills/grove-auto/SKILL.md` (create folder + `feature.md` with `flow: auto` + `00-ticket.md`; one researcher subagent maps the code; stateless-CTO relay loop with the question tool; Outcome Brief + play-back confirm; planner writes `03-plan.md` with Decisions and Slices; ends naming `grove-approve <slug> plan`); `skills/grove-run/SKILL.md` + `references/slice-mode.md` (parent: gate on approved `plan`, commit-or-ask, worktree via first child, loop per D4 (`grove new --child … --wait`, completion read from git), stop after every slice; child: plan the slice into `04-run.md`, implement itself, run the slice's verification, commit); `skills/grove-approve/SKILL.md` (`plan` in its units list); `shared/approve.md` (+ `plan` unit, question-tool prompt in `auto`); `shared/contract.md` (`auto` flow, files per feature, `01-outcome.md` carries the standard frontmatter (`status`, `version`, `based_on: []`) and an empty `## Open questions`; rule 9 if still missing, see D7); `shared/MANIFEST`; `commands/grove-auto.md`, `commands/grove-run.md`; `scripts/validate.sh` (`AskUserQuestion` check). Run `scripts/sync-shared.sh` and `install.sh`.
**Verification.** (1) `bash scripts/validate.sh` passes. (2) Manual, in a scratch git repo with `grove.config.json`: ticket "add a `hello.txt` containing hello, then a `goodbye.txt`"; run `grove-auto`, observe every human question is an `AskUserQuestion` (no chat questions), confirm the brief; `grove-approve <slug> plan` sets the three files approved; `grove-run <slug>` (answer "continue" between the two slices) creates one worktree, a session group (parent + children) in the sidebar, exactly two commits `<slug>: slice 1 — …` / `slice 2 — …`, and a `04-run.md` with both slice sections `Status: done`. Review note: until Slice 2 the app shows a `flow?` warning on this toy feature (unknown flow value falls back to `full`); that is expected. This slice is the first human review point.

### Slice 2. `auto` flow in the app, no card warnings

**Outcome.** The app discovers an `auto` feature with stages Outcome → Research → Plan → Run and no `flow?` warning; existing flows are unchanged.

## Deviations from the brief the human should know

- A halted or finished run is reported as the parent session's last line; the sidebar card shows only `waiting` (the app has no message field and none is added).
- `04-run.md` lives in the run's worktree/branch, so the main checkout's card shows no run progress, the options file is opened at its worktree path, and `grove-approve <slug> run` is run from a session in that worktree; the human then commits the approval and merges or opens a PR.
- Unattended slices work only if the human's own Claude settings already allow edits and the project commands; otherwise the run stops at the first prompt. The slice-1 gate lists the Bash prefixes the parent needs.
- The Features board draws only the stages the project's features use (Slice 3): legacy-only repos look as before; an all-`small` repo shows two columns and a repo with no features an empty board.
- `grove-run` may ask to commit the approved plan folder first. `04-run.md` records models *requested*. `grove-auto`'s own session keeps the human's model; only its subagents use the profile. The CTO interview has a soft cap of 8 questions. The plan is at 8 of 8 allowed decisions.
- Shared skill files (`contract.md`, `gates.md`, `approve.md`) gain additive `auto` text that syncs into every existing skill; legacy behaviour is unchanged.
- Dependencies on other people's uncommitted work: the question-tool edits in the skills repo (D7) and the `--base` worktree work in the app (Slice 1 and 5).

## Risks and what is deliberately not done

- **Risks.** The parent reads state from git (`git -C <worktree>`), which may still trigger a one-time permission prompt that surfaces to the human. A repo without pre-approved edits halts the run at the first child prompt (by design, see D4). The sidebar shows only `waiting` for a halted parent; the one-line reason is in its session, not on the card. Subagent models are *requested*, not verified. Worktree lock is per project, not ref-counted, so a child must be killed only after its gate and before the next slice's child starts (the rule in D4 does that). `grove-run` is a two-mode skill; the child prompt must carry `--slice N` so the modes cannot be confused. The relay CTO depends on the planner passing the question through unchanged.
- **Not done.** Custom roles or role prompts, OpenCode, an app orchestrator, a run view, auto-start on approve, per-slice risk tags, user-global profiles, notifications, a settings UI, changes to existing flows or skills, fixing the stale `grove-plan` text, adding `commands.dev` to the config schema, run progress on the main checkout's card.
