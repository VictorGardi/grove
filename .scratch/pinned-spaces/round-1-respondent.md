# Round 1: respondent answers (pinned spaces)

Checked against code at fe348e2: core/store/state.ts, core/spaces.ts, ui/quiet-spaces.ts, ui/goto-model.ts, tauri.conf.json, plus the four research notes and GLOSSARY.md / ADRs 0001-0006.

## Q1 Where do pins live
Answer: in Grove's own saved state (~/.grove/state.json), as an optional field on the space's saved record, not in per-window settings. Tag: inferred. Confidence: high on the home, medium on the exact shape.
- Evidence: per-window settings are webview localStorage that nothing syncs (no `storage` listener) and a blocked store silently falls back, so "same in every window" and "survives a restart" cannot be met there. The saved space record is deleted by `removeSpace` (spaces.ts:107-114), so "a pin vanishes with its space" is automatic with no pruning code. Today the app has ONE webview window (tauri.conf.json, capability list `main`); "every window" in practice means the core plus CLI clients and any future window. Do not promise more than the core broadcast gives.
- Shape matters for Q3: a bare `pinned: true` loses the order. Save a pin time (`pinnedAt`) on the record, so order is stable and still vanishes with the space. The validator (`isSpaceRecord`) ignores extra keys, and rename keeps unknown fields (spread), so no version bump and an older Grove keeps working (it would drop the pin only if it rewrites the record from scratch; it does not).
- ADR? Yes, a short one is justified. It is hard to reverse (a field in the user's state file), it is surprising next to the eight window-local prefs (`.scratch/persisted-prefs` said all prefs stay in browser storage), and it has a real trade-off. It should record: pins held by the core on the space record, shared, removed with the space; rejected: window localStorage; rejected: a separate pins list keyed by id (needs pruning, can go stale, as ADR 0005's folds do). Not needed: the visual choices.
- Strongest alternative: a separate `pins: string[]` in the state file (gives order for free, easy to list). Cost: stale ids to prune on every removal path, and a second place that must agree with the space set. User would see the same thing until a pruning bug leaves a ghost pin. Second alternative, localStorage: the user would lose pins when site data is cleared and see different pins if a second window ever exists; fails the stated "done" test only in those cases but violates "every window shows the same".
- Also needed: pin/unpin is a core write, so it fails while the state file is refused (version mismatch). The window must show that like other refused writes; the user otherwise taps the shortcut and nothing sticks.

## Q2 Cmd+1..9 and the active row
Answer: Cmd+1..9 keeps numbering the tree only; Pinned group rows have no numbers. Tag: inferred. Confidence: medium-high.
- Evidence: `sidebarSpaceOrder` feeds Cmd+digit, Go to's starting order and `dropSpace`'s fallback selection (window-store.ts:426); a test asserts every row is numbered whether folded or not. Putting the Pinned group first would silently renumber every shortcut the moment a space is pinned, and the user has muscle memory. Counting each space once (tree) means no duplicate numbers.
- Surprise if the other way: pinned first renumbers shortcuts on pin; and a number that is not drawn anywhere (numbers are not shown on rows) cannot be learned from the screen. Surprise with the interviewer's answer: the user pins their most used space and Cmd+1 still goes to something else; acceptable because pins are "come back to", not "hotkeys". Mention this as a possible later addition, not now.
- Active row: highlight BOTH copies (selected background), and put `aria-current` on the tree copy only (keeps tests that look for one `aria-current` row, and one current item for screen readers). Tag: inferred; confidence medium. Alternative: only the Pinned copy highlights when the pinned group is the user's route in: the user clicked there and sees feedback where the eye is, but the tree loses its "where am I" marker, and the forced-open heading rule (active heading draws open) still makes the tree copy visible anyway, which then looks unselected. Highlighting both is the least surprising. If only one: a user who clicks a pinned row and sees the tree row also selected is not surprised; a user who sees the tree row selected but not the pinned row below it might think the pin is not the space.
- Test risk: `listed()` in status-window.test reads every `#spaces .space-name`; a Pinned group inside `#spaces` changes it only when pins exist (default test has none).

## Q3 Order inside the Pinned group
Answer: pin order, newest at the bottom. Tag: inferred. Confidence: medium. Needs-human only if the user wants "drag to reorder", which is a non-goal today.
- Evidence: Recent order is per window and not saved, so ordering by recent use would make the group reshuffle as you work and differ between windows, which defeats "remember where to go back to after a weekend". Tree order changes when repos are added. Pin order is the only stable, shared order, and needs `pinnedAt`.
- Strongest alternative: newest pin at the TOP (what many chat/bookmark apps do): the thing you just pinned is the thing you are about to leave, so it is the most likely to be wanted first next Monday. Cost: the list shifts on every pin. Another: most urgent first: it reshuffles while you look, and the row already shows state; rejected. This is a cheap-to-change choice (no data change, only sort), so it is not an ADR matter.

## Q4 How the window shows the pin
Answer: (a), a pin button at the left of the tab strip, filled when pinned, click toggles, tooltip shows the shortcut. Tag: inferred. Confidence: medium-high. Also yes to a Pin/Unpin item in the sidebar space context menu, and a pin mark on the Pinned and tree rows (always shown on the tree row of a pinned space; not hover-only).
- Evidence: the tab strip is always visible even when the sidebar is hidden (`grove.sidebar-hidden`), and the sidebar row is the only marking today, so with the sidebar hidden the user has NO way to see the pin without a strip control. (d) is dead: the title bar is `hiddenTitle` with Overlay style and nothing sets a title. (b) repeats the mark once per pane in grid mode and the pane header is a drag handle; wrong granularity (pin is per space). (c) adds a new space label, a larger change that also needs width on a crowded strip. Keep (a) shown even when the space has no tabs.
- The button must act on the active space, not on a row: with no active space it is hidden or disabled.
- Shortcut: Cmd+Shift+P and Cmd+D are unbound today (Cmd+Shift+D is Changes). Cmd+Shift+P is the least collision-prone; it must also go through KEY_ACTIONS, KeyAction, DEFAULT_VALUES, KEY_DESCRIPTIONS, KEY_LABELS, keyActions in main.ts and the README line. It is rebindable like every key. A matched chord never reaches the terminal/agent (capture + stopPropagation), so check that Cmd+Shift+P is not what an agent in the pane expects; the research says unverified. Tag: needs-human is not needed, but verify with the agents used.
- "Focused window": beyond this reading, it could mean (i) the window that has keyboard focus when more than one exists (there is one today), (ii) the focused pane in grid mode, whose space can differ from the active space only if the grid mixes spaces. Check: can grid tabs come from other spaces? `gridTabs` are tab ids and the tab strip shows only the active space's tabs, so a grid pane could belong to another space. The pin button follows the active space (the one the strip shows); the pin mark in a grid pane header for another space's tab is NOT covered. Flag, low-medium confidence, as a small gap for the user's confirmation (decision-log item 3 already marks this "to confirm").
- Alternative's effect: (b) is closer to what you are looking at in grid mode but is repeated and busy.
- Go to cannot pin (it only navigates; glossary), so pinning is from the strip button, the shortcut and the sidebar menu. Tag: decided (glossary).

## Q5 Go to, pinned first
Answer: partly agree. With no search words, a pinned block first is what the user asked for (decision 2). Tag: decided for "pinned first", inferred for the rest. Confidence: medium; the burying question is needs-human.
- Does it bury a needs-you space? Yes: a non-pinned needs-you space would sit below every pinned space, reversing today's strict "needs you first" tier order (goto-model tiers 0-4). The mitigations that exist: the needs-you chip, the urgent banner and Cmd+. (next-urgent). Also the pinned block still shows each pinned space's own state indicator, so a pinned needs-you space is seen. The user took the recommendation without seeing this cost, so this specific trade-off is `needs-human` (it changes what Enter in Go to does first). My lean: keep the user's words (pinned first) but sort inside the block by pin order, and keep urgency visible via the chip.
- Alternatives: (1) tiers unchanged plus a pin mark: nothing buried, but fails "lists pinned first". (2) Pinned first only inside each tier: needs-you still first, pinned lead their tier; satisfies the urgent-first rule but the pinned set is no longer one block, so it does not serve "where was I" and would not match the Pinned group order. Impact on the user: with (2), after a weekend with no agent activity everything is tier 4 and pins lead anyway, which is the Monday case. This is an honest candidate; I would offer it to the user as the alternative.
- Duplicates: a space listed in the pinned block AND in the tree below it gives two rows with the same tab ids; Go to uses `tabId` as row identity and `highlight` picks by `tabId`/`key`, so double rows risk a wrong or duplicate highlight. Recommend: in Go to a pinned space appears ONCE (in the pinned block), unlike the sidebar. Tag: inferred, medium. Note this differs from the sidebar, which duplicates by the user's explicit ask.
- With search words: keep the ranking and show a pin mark; do not float pinned above a better match (it would put a worse match first). Inferred, medium-high. A user typing a name wants the best match; the mark is enough.
- Highlight start: today it is the current tab (empty query); keep it. Do not make the highlight start on the first pinned row.

## Q6 Quiet spaces
Answer: agree in outline, with one correction. Tag: inferred. Confidence: medium.
- Evidence (quiet-spaces.ts): quiet = not active/worktree/under-heading, nothing busy, not among 5 most recently visited. Pin is not part of it, and a shared function feeds both the sidebar and Go to, so the pinned rule belongs OUTSIDE `quietSpaces` (a caller removes pinned ids from the quiet set for the Pinned group and Go to's pinned block); do not add pins to `quietSpaces` itself or the tree copy would stop folding too. Tests (quiet-spaces.test, sidebar-model foldQuiet, status-window quiet test) require: the heading leaves only when all its rows are quiet; counts count spaces; none when nothing is quiet. These stay true if the tree copy keeps the normal rule.
- Tree copy folds as normal: the user's intent is "also stays in its place" but "quiet" is the sidebar's way of hiding idle stuff; a pin should not force clutter back. Risk: a pinned space can vanish from the tree behind "N quiet spaces" while showing in the Pinned group, and the count includes a space you can see. My lean: exclude pinned from the count and from the fold (i.e. pinned spaces are never quiet anywhere, tree copy included), which avoids the "count includes a visible space" confusion, but then the tree gets bigger and a heading never folds away while it holds a pinned space. Both defensible; the interviewer's rule is more conservative to the existing tests but gives the count surprise. Tag: needs-human, low confidence, cheap to change, so decide the simple one (never quiet in the group and Go to, tree copy normal, count counts spaces folded in the tree) and revisit only if it looks wrong.
- Cost of "each pinned space counted once": a reader of "3 quiet spaces" opening the fold sees a space already shown in Pinned. Fine.

## Q7 Missed: one-way doors and surprises
1. Name the term. GLOSSARY lacks Pin and Pinned group; the Heading definition says a grouping of a repo, so the Pinned group is not a Heading (and the sidebar test asserts `#spaces .heading` lists exactly repos, so the group must not use `.heading`/`.heading-name` classes). Tag: inferred, high.
2. Deleted worktree folder outside Grove: the space record stays, `readGit` returns nulls, the space becomes a plain row (no branch, no repo) and stays pinned; the Pinned row loses its repo name and now looks like another space. This is consistent with "pin goes only when the space closes". Nothing removes it. A dead pin is arguably the right result (the user still sees it and can close the space). Tag: inferred, medium. Alternative: auto-unpin when the folder is gone; it would silently erase "where I was". Do not. Related: shells for it restart in the home folder.
3. Two spaces on the same folder: pins are by space id, so pinning one does not pin the other; the Pinned rows would have the same name and repo and look identical. Row title is the path (same). Surprise: pin one, both seem pinned. Fix: show the pin mark on the tree row of the pinned one only (naturally true). Medium.
4. Re-adding a closed space gives a new id, so it is not pinned again; say this plainly in the ADR (user stated "vanishes with it" - decided).
5. A pinned worktree space that is removed through Grove: pin goes; the Pinned group must update through `spaces.removed`, and `dropSpace` must not rely on pinned order.
6. Restore on startup: pins come from the core with `spaces.list`, so the group draws on first paint with the saved view state; no dependence on `grove.view-state`. A pin for an id missing from the list is not drawn. Medium-high. Folded heading force-open rule: clicking a pinned row for a space under a folded heading opens that heading (active heading draws open): a visible side effect; decide it is fine (yes, consistent with today).
7. Should the Pinned group itself fold? Not requested; keep it always open and unfoldable (no new stored preference). If it is foldable it needs the roll-up rule and a stored pref (ADR 0005 pattern). Recommend no fold. Inferred, medium.
8. Empty Pinned group: draw nothing (no empty heading) until the first pin; a one-line hint is optional. Inferred.
9. Cmd+1..9 index is built from the tree only, but `dropSpace` and `reconcile` pick fallback spaces by order; unchanged.
10. CLI: the core owns pins, so `grove` could list/pin later; out of scope. Adding `pinned` to `SpaceInfo` is additive and visible to the CLI; make sure its output tests do not compare whole space objects.
11. Per-pin display of repo name: derived, not saved (ADR 0002 spirit); two spaces named the same in different repos are told apart by it.
12. The git poll broadcasts `spaces.changed` when the SpaceInfo JSON changes; a pin toggle will therefore go through the same path, so all clients agree without a new notification.
