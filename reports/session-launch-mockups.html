grove · design exploration

A way to trigger a session and choose its settings

Today the GUI can only start a session with { projectId, kind }. The command palette lists project × kind rows; there's no form, no sandbox toggle, and no way to make a worktree from the app. Everything else you want — prompt, label, feature, sandboxed — already works in core and is reachable from the grove new CLI, but the IPC channel type is narrower than the core command, so the renderer literally cannot send it.

Three shapes below. All three cover the same settings, because all three write the same session:create payload — they differ in where the settings live and how much ceremony the happy path costs.

Option A

Command strip — settings live in a bar under the prompt

⌘T opens one overlay with a prompt on top, results in the middle, and a persistent row of setting chips pinned to the bottom. Each chip opens a flyout; nothing is modal. Tab moves through the chips, 1–9 picks inside an open flyout. ↵ always launches — you never leave the strip.

Why it works

  • Zero ceremony on the happy path. ⌘T → type → ↵. Settings that already match are invisible.
  • Fast for the settings you change often — worktree toggle and sandbox are one chord away.
  • Reuses the palette you already have. One fuzzy surface for sessions, features, projects and now config.
  • ⌘J stays a fast path — a terminal launch never needs to touch this.

Where it hurts

  • Discovery problem. New users never find the chips; the whole value is invisible until you know it exists.
  • Chip soup. Six chips is the ceiling before it wraps into two rows and becomes a form again.
  • Flyouts hide the consequence. Choosing "sandboxed" in a dropdown tells you less than a live sentence does.
  • No room for presets without turning the chip row into a second list.
Option B

Launch dialog — one form, four visible fields, one disclosure

⌘T opens a centred dialog. Everything 90% of sessions need is visible; label, cols/rows and grid-add sit behind one Advanced… disclosure. The sandbox toggle carries a live one-line consequence that flips with the switch. It's built almost verbatim from Modal + ConfirmDialog + LinkPicker + CommentEditor — four components grove already has.

Why it works

  • Self-documenting. Someone who has never seen grove can start a correct session in one look.
  • Isolation is first-class, right where the choice is made, with its consequence written out in full.
  • Almost free to build. Modal, ListRow, the LinkPicker list, the CommentEditor textarea and the error line all exist.
  • Progressive disclosure, two levels max — the rest is one collapsed row.

Where it hurts

  • Punishes the repeat case. The 10th session this hour pays for a dialog it doesn't need.
  • Focus theft. Every launch costs a modal; the terminal loses focus.
  • No home for defaults. "Remember this" wants a settings pane this shape can't reach.
  • ⌘J is now ambiguous — does the fast path still exist, or does everything go through here?
Option C

Side rail — presets on top, compact form below

A persistent right-hand rail that docks alongside the content area instead of covering it. Named presets sit at the top: pick one and every field below fills in and stays editable. This is the only shape that answers "what settings do I usually want?" — and the only one with room to grow into a real defaults pane.

Because the rail docks rather than overlays, you keep sight of the running session you're steering — the thing a modal takes away.

Why it works

  • Presets are the real answer to "choose settings". One click replaces six decisions, and every one stays editable after.
  • Never blocks. Sessions keep running behind it; you can read a diff and launch the next agent in the same glance.
  • Scales. A fifth setting costs a row, not a redraw. Model, effort and defaults can land here later.
  • Presets are shareable — a named profile that captures kind + worktree + sandbox, per project.

Where it hurts

  • Most expensive of the three. A third docked region, a new shell slot, collapse state, responsive widths.
  • Steals width from the terminal, which is the one thing people came to grove to watch.
  • Presets need a storage story — per project? per user? committed to the repo? That's a real decision, not just UI.
  • Still modal in spirit: it interrupts the same way a dialog does, just prettier.

Wiring

What every option has to touch

Independent of which shape you pick, this is the shared work — and it's smaller than it looks, because core already accepts every field.

The blocker

src/shared/ipc.ts:15 declares 'session:create': [{ projectId, kind, cols, rows }, Session] — narrower than Commands.sessionCreate at src/core/core.ts:75, which already takes cwd, prompt, label, feature, sandboxed. Everything the CLI can do today is unreachable from the renderer purely because of this one type. Widening the tuple is step one and it's mechanical.

Worktrees need a new IPC surface

There is no worktree:add channel. Today only cliServer.ts:91 calls worktrees.add(), then registers the checkout and lets sessionCreate resolve it as a project (ADR 0037). The GUI needs that promoted to a command, so it can make the worktree before the session exists and surface worktree-failed / conflict inline.

Decide what "remember this" means

Every serious tool resolves defaults in a visible order — Cursor does user → team → system, and its copy states the point: "Default repository — supplying a repo here lets users skip that step". For grove the question is whether defaults live in grove.config.json, in app config, or nowhere. If nowhere, presets (Option C) are the only place the answer can live.

One bug to fix before promising anything

sessionResume (core.ts:774) builds its argv with st.source.argv(id, 'resume') and no sandbox wrapper — so a resumed sandboxed: true session comes back unsandboxed. ADR 0033 says it should stay sandboxed. A UI that says "stays sandboxed on resume" is making a promise the code doesn't keep yet.

Payload every mockup sends — session:create
{ "projectId": "9f3c", // grove/session-launch, registered as its own project (ADR 0037) "kind": "claude", "sandboxed": true, // persisted, so a resume never widens (ADR 0033) "feature": "2026-10-11-session-launch", "label": "Session launch", "prompt": "implement slice 3 of session launch", "cols": 120, "rows": 40 }
