# The container blocker was never real; Seatbelt still trades security for speed

**grove would not hit the same problem under Seatbelt — but the comparison no longer has to be made under pressure, because the fault that prompted this research turned out not to be real.** Three findings drive this. First, **the ENODEV "mount failure" that blocked ADR 0034 was a misdiagnosis in our own investigation, not a property of Apple `container`.** The true cause is that **`container run -i -t` requires a real controlling TTY on the host**: from a shell with no TTY on stdin it fails with `NSPOSIXErrorDomain Code=19 "Operation not supported by device"`, and from a PTY it succeeds. Measured 2026-10-11, the same command with `-i -t` fails without a TTY and passes under one; `-i`, `-t`, or no flags pass either way. Every mount failure we recorded on 2026-10-10 was a run that also carried `-i -t`, which is the flag grove's design uses. **grove is unaffected**, because its leaf command runs inside a tmux pane, which always has a real PTY (MEASURED, this machine; see the correction note). The container path was then confirmed working end to end, including a real `git commit` inside a sandboxed worktree that the host could see. Second, **Claude Code's macOS sandbox is architecturally not grove's use case**: Anthropic documents that it confines individual Bash/PowerShell/Monitor invocations and that the agent process, its file tools, MCP servers, and hooks run *outside* it, and explicitly recommends a container, VM, or the standalone sandbox runtime for a boundary around the whole process ([Anthropic docs](https://code.claude.com/docs/en/sandboxing), CITED) — so grove cannot "just use Claude Code's sandbox", it must generate its own profile, which is a different and harder undertaking. Third, and equally important, **every published macOS agent-sandbox escape is a policy-generation bug rather than a Seatbelt bypass**, but there is one escape class no policy rule can express — inherited file descriptors — and it is grove-specific precisely because tmux servers are long-lived ([`sandbox(7)`](https://keith.github.io/xcode-man-pages/sandbox.7.html), CITED; reproduced MEASURED by our own researcher, and independently confirmed by Chromium's own design docs). Seatbelt is real kernel-enforced MACF, it works, and it is genuinely cheaper in engineering terms — it deletes the image subsystem and the OpenCode bridge entirely — but it is **structurally weaker as a security posture**, and under an actively adversarial agent that difference decides the question. All grove artifacts (ADR 0034, ADR 0035, ADR 0036, `docs/work/2026-10-08-agent-sandboxing/`) are untouched by this research; changing the mechanism is a design revision requiring an explicit human decision, not an implementation detail.

*Epistemic labels used throughout: **MEASURED** = someone ran it (I mark "this machine" for runs on the maintainer's Mac, or attribute the machine for others); **CITED** = public source with URL and date; **INFERRED** = my reasoning. Claims recovered by reverse-engineering shipped binaries have been excluded entirely and are not used anywhere in this report.*

## Claude Code sandboxes the command, not the agent

Anthropic documents the mechanism unambiguously. On macOS "the sandboxed Bash tool uses operating system security primitives… **Seatbelt** for sandbox enforcement"; the open-source runtime it builds on states that it uses "`sandbox-exec` on macOS" with "**dynamically generated** Seatbelt profiles" ([Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing) and [`@anthropic-ai/sandbox-runtime`](https://github.com/anthropic-experimental/sandbox-runtime), both CITED, accessed 2026-10-10). So the user's premise is correct at the level of mechanism. Everything after that is where it stops being the same problem.

The boundary Anthropic draws is around **shell invocations**, not the agent. Their docs say verbatim that "the limits apply to **Bash, PowerShell, and Monitor commands and the processes they start**," that "**the sandbox covers shell commands only**," and that Read/Edit/Write/WebFetch, MCP servers, command hooks, plugin monitors, LSP servers, and helpers like the statusline command and `apiKeyHelper` "run with your full access" ([Anthropic](https://code.claude.com/docs/en/sandboxing), CITED). Their own comparison table ranks it last of five options, and states that "every other approach in the table puts the whole Claude Code process inside the isolation boundary" — with VM ranked above container above sandbox runtime above the Bash tool ([Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments), CITED). The advice for grove is written in their own words: "To put the tools, processes, and commands in this section behind one boundary, run the Claude Code process itself in a **container, virtual machine, or the sandbox runtime**" ([Anthropic](https://code.claude.com/docs/en/sandboxing), CITED).

That matters because grove's guarantee is a guarantee about *the agent session*, not about individual commands. An agent's Read tool writing to `~/.zshrc` or its own `~/.claude/settings.json` is not a sandboxed Bash invocation; it is agent code running with the user's full authority. Under Seatbelt, grove would have to generate its own SBPL profile and apply it to the whole process tree — which is what the standalone runtime does, and which means grove becomes the author of the policy that the four major vendors collectively get wrong (see the CVEs below). There is also no public Claude Code CLI flag that turns the sandbox on; it is enabled via `sandbox.enabled` in a settings file or the `/sandbox` command ([CLI reference](https://code.claude.com/docs/en/cli-reference), CITED), so a grove launcher would have to inject `--settings '{"sandbox":{…}}'` — fine, but that is the *inner* control, layered under whatever outer boundary grove chooses.

Two more properties of Claude Code's configuration matter for grove even as an inner layer. `sandbox.enabled` **defaults to `false`**, and `failIfUnavailable` **defaults to `false`** — meaning if the sandbox cannot start, Claude Code runs commands *unsandboxed* rather than failing ([settings reference](https://code.claude.com/docs/en/settings-reference) and [sandboxing docs](https://code.claude.com/docs/en/sandboxing), CITED). A grove-supervised deployment would want the opposite polarity, but it cannot get it from a repository settings file: `allowUnsandboxedCommands`, `filesystem.disabled`, and the managed-policy locks are only settable from user, managed, or `--settings` scope. That is an argument for grove owning the outer boundary outright rather than delegating.

## Seatbelt filters access; it never gives a restricted view

Seatbelt is a TrustedBSD-derived MACF policy attached to the process's credential label, evaluated by the kernel on each controlled operation. Enforcement is real and **MEASURED**: denials appear in the kernel log as `kernel[0:...] (Sandbox) echo(90341) deny(1) file-read-data /` (MEASURED, this machine, macOS 26.4.1). A sandboxed process **cannot lift its own policy**, verified three ways on this machine: calling `sandbox_init` on an already-sandboxed process fails with `profile not found` and leaves the original policy fully enforced; `exec`ing `sandbox-exec -p '(allow default)'` from inside a sandbox fails with `sandbox_apply: Operation not permitted`; and the policy survives arbitrary `exec` depth (`sh → sh → sh → cat` was still denied) (all MEASURED, this machine). Apple's `sandbox(7)` states the inheritance rule plainly: "New processes inherit the sandbox of their parent" — which is the property grove wants, since it means the whole agent process tree is confined by construction rather than by cooperation.

What it cannot do is the more important half of the story. **MEASURED on this machine:** the mount table is byte-identical inside and outside the sandbox (`/sbin/mount | md5` matches exactly, and the sandboxed process sees the host's real APFS device topology including the sealed system volume); `chroot` is *denied* rather than *provided*, confirming there is no view-isolation primitive at all; there is no PID namespace (`ps -p 1` shows host `launchd`); macOS ships no `unshare` binary at all, and `mount -t tmpfs` inside the sandbox fails with `invalid file system`; `uname -a` returns the host kernel verbatim. So Seatbelt answers "what may this process do?" and never "what does this process see?" Under Apple `container`, the jail **is** a mount table — an enumeration, in one place, of every path that exists inside it. Under Seatbelt the jail is a hand-maintained list of exceptions from `deny default`. That is the whole structural difference, and it is why the two designs fail differently: a container mount error is loud and total, while a Seatbelt rule mistake is silent and partial.

That asymmetry is not theoretical. **MEASURED, this machine:** writing a deny rule *before* a broader allow silently disables it — a profile with `(deny file-read* <secret>)` followed by `(allow file-read* <parent>)` printed the secret's contents. The same deny written *after* the broad allow correctly returned `Operation not permitted`. Seatbelt is **last-match-wins**. This resolves a conflict between our researchers, and it matters a great deal: the grove constraint-mapping note recorded the opposite rule ("**first match wins**… carve-outs must be written *before* the broader allow") and the seatbelt-fundamentals note also asserted first-match-wins while admitting it could not find a primary source. Both are wrong. Anthropic's own runtime source says it outright — "**Seatbelt is last-match-wins**" — and builds an entire re-emission layer (`lateReadDenyFilters`) whose stated invariant is that "every filter here is a deny or a narrower deny: nothing this function produces can make a path readable that is not readable today" ([sandbox-runtime source](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/macos-sandbox-utils.ts), CITED, verified by direct fetch 2026-10-10). My measurement agrees with Anthropic and against both of our notes. **If grove had built a profile generator to our own notes' specification, the carve-outs would have been silently inverted and every protected path would have leaked.** That alone is a process finding: the notes' conclusions cannot be trusted where they conflict with a primary source we can read.

A second conflict resolves in our favour's disfavour. The prior-art note cites Microsoft's `mxc` as declaring that Seatbelt has "no such primitive" for IP, CIDR, **port**, or protocol filtering ([mxc](https://github.com/microsoft/mxc/blob/main/docs/seatbelt/seatbelt-backend.md), CITED). But **MEASURED on this machine:** `(allow network-outbound (remote ip "*:443"))` permits direct-IP HTTPS (got a real `401` from `api.anthropic.com`) while blocking plain HTTP on port 80 (`000`), and `sandbox-exec` *rejects* a literal destination IP outright with "host must be `*` or `localhost` in network address". Anthropic's production profile relies on exactly this — `(remote ip "localhost:<proxyPort>")` — so port-scoped rules are real and in service. The accurate statement is narrower than `mxc`'s: **Seatbelt can do all-or-nothing and port-scoped filtering, but cannot filter by destination hostname or address.** This partially reopens ADR 0036, whose premise that the container offers "no enforcement primitive" for egress is true of the container and false of Seatbelt, which can express a deny-all and is strictly stronger than the container's measured default-open posture.

## Every constraint gets cheaper; one guarantee gets structurally weaker

Mapping grove's ten committed constraints against both mechanisms, Seatbelt is **easier or equal on all ten as engineering** — and worse on one as security. The single largest reduction is constraint 7: **MEASURED on this machine**, `node v26.3.0`, `claude 2.1.285`, and `opencode v2.0.20` all ran natively under a deny-default profile with no image and no build, and `sandbox-exec` startup measured **~6 ms per invocation** (20 runs, 0.124 s total vs 0.023 s for bare `/usr/bin/true`). I closed most of the headline performance gap from the prior-art survey: a 2,000-iteration create-and-read workload ran in **2.71 s sandboxed vs 2.78 s unsandboxed** — within noise, i.e. **no measurable per-syscall enforcement cost** (MEASURED, this machine). Caveat: that is a file-I/O microbenchmark, not a real build workload, so it bounds rather than settles the question. Eliminating the image subsystem also eliminates the 28 s first-session build and the maintenance of pinned Linux copies of two agents that must be re-pinned on every upgrade.

Constraint 5 is the other decisive win: because a Seatbelt sandbox shares the host's loopback, the OpenCode service is reachable as-is, so **D6 evaporates entirely** — no bridge-address discovery, no rebinding the host service off loopback, no `0.0.0.0` LAN-exposure risk, no consent prompt, no second-registration eviction hazard, no orphan-container pruning (MEASURED: a Python AF_UNIX server answered from inside the profile). Constraint 6 flips from impossible to a policy choice: **MEASURED on this machine**, a deny-default profile blocking `~/Library/Keychains` made `security find-generic-password` fail with rc=44 and `login.keychain-db` return EPERM, while a profile granting `com.apple.SecurityServer` plus the Keychain subpath returned the secret verbatim. Under the container, credentials are an unavoidable casualty; under Seatbelt they are an explicit, enforceable decision — and the right default is deny.

| # | Constraint | Container (today) | Seatbelt | Verdict |
|---|---|---|---|---|
| 1 | Host-identical paths | mount table + same-path invariant | free — path filters are inherently host paths | **easier** |
| 2 | Worktrees | mount worktree **and** common dir; experimental `--read-only-path` for `hooks`/`config` | same two-path requirement, plain ordered denies | **same**, fix is inherent |
| 3 | Git hooks execute | runs as uid=0 inside the jail | runs, but blast radius confined by policy | **same**, smaller blast radius |
| 4 | `~/.gitconfig` read-only | experimental `--read-only-path` | one allow-read, no allow-write | **easier** |
| 5 | Spool + grove socket | mount both + the whole D6 bridge | subpath allow + one `network-outbound` literal | **easier** (deletes D6) |
| 6 | Credentials | impossible (Linux VM) | denyable **and** grantable | **easier** (becomes policy) |
| 7 | Native binaries | image build, 28 s first run, pinned Linux agents | none; host binaries run natively | **easier** (deletes image) |
| 8 | Network | none | deny-all + port-scoped; **no host allow-list** | **easier** for deny-all |
| 9 | Placement | `container run` as leaf argv | `sandbox-exec -f` as leaf argv | **same** |
| 10 | Rollback safety | loud mount/build errors | **silent rule mistakes** need a canary probe | **easier**, worse failure mode |
| — | **Inherited-FD escape** | **impossible** (fd points into the jail) | **reproduced; no rule can close it** | **structurally weaker** |

Now the guarantee that breaks. Apple's `sandbox(7)` states that restrictions are enforced **on acquisition** of resources: "if the application already has a file descriptor opened for writing, it may use that file descriptor regardless of restrictions" ([sandbox(7)](https://keith.github.io/xcode-man-pages/sandbox.7.html), CITED). **MEASURED on this machine:** a parent opened a write FD to a file outside the sandbox and passed it down; the sandboxed child wrote through `/dev/fd/3` under a profile containing `(deny file-write* (literal "<that exact path>"))`, and the marker landed on the host. The deny was correct, fully specified, and bypassed. Chromium exploits the same property deliberately — "a common pattern is to first open any needed resources, then apply the sandbox policy" ([Chromium Mac Sandbox README](https://chromium.googlesource.com/chromium/src/+/HEAD/sandbox/mac/README.md), CITED) — which is the strongest possible evidence that this is by design and not an oversight.

**This is grove-specific, and it is why it must not be softened.** Claude Code wraps each command at `exec` time from a parent that holds almost nothing open; a tmux **server** is long-lived and holds descriptors open to its sockets, its cwd, and whatever the session was started with, and every pane is a descendant of it. So the process grove would confine inherits a capability set grove did not choose. The mitigation is tractable — close non-stdio FDs at the `sandbox-exec` boundary, which grove controls — but **how many usable write FDs grove's actual Electron → tmux-server → pane chain leaves inheritable is unmeasured**, and that is the first thing to spike. Stating it precisely: Seatbelt preserves "the agent cannot *name* a path outside its working directory." It does **not** preserve "the agent cannot write outside its working directory," because a descriptor it never has to name can still be written through.

## Every published escape is a policy bug, and the profile debt is the real cost

The pattern across the entire corpus is consistent and unusually well-attested: **the MACF primitive held; the policy generator failed.** Codex CLI **CVE-2025-59532** (High, 19 Sep 2025) treated a *model-generated* `cwd` as the sandbox writable root, letting an agent write and execute outside the folder the user started in; the fix was to derive the boundary from the invocation site instead ([GHSA-w5fx-fh39-j5rw](https://github.com/openai/codex/security/advisories/GHSA-w5fx-fh39-j5rw), CITED). Claude Code **CVE-2026-55607** (High) allowed worktrees named `.git` and navigation outside the sandbox context, and via symlink manipulation plus `git fsmonitor` execution achieved "code execution outside of seatbelt sandbox restrictions" — precondition being a malicious cloned repo with prompt injection ([GHSA-7835-87q9-rgvv](https://github.com/anthropics/claude-code/security/advisories/GHSA-7835-87q9-rgvv), CITED). Claude Code **CVE-2026-25725** is the cleanest illustration of the recurring root cause: the config file `.claude/settings.json` was unprotected **when it did not exist at startup**, so sandboxed code created it and injected `SessionStart` hooks that ran with host privileges ([GHSA-ff64-7w26-62rf](https://github.com/anthropics/claude-code/security/advisories/GHSA-ff64-7w26-62rf), CITED). Note the cross-platform point: that one says "bubblewrap" in its text but the escape concept — create-if-missing a file the writable parent lets you create — is mechanism-independent.

The mandatory design rule falls straight out of the three: **no value produced by the model or by filesystem traversal at runtime may define the sandbox boundary.** Compute it at the invocation site, canonicalise it, emit deny rules whether or not the path exists, and **fail closed on any path that will not compile**. The last clause is not optional — Anthropic's changelog is a catalogue of path-metacharacter bugs where rules were silently dropped: parentheses in a path "being dropped as invalid or ignored by the Bash sandbox, which left 'read-only' folders writable"; a NUL byte "expanded into a wildcard match"; an unclosed `[` producing an invalid regex. All CITED from the [Claude Code CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md). Our own measurement adds a fourth instance: an under-specified deny-default profile that blocks the root inode does not emit a sandbox diagnostic — **dyld aborts with SIGABRT** inside the dynamic loader (MEASURED, this machine; the same root cause appears in Anthropic's source as issue #190).

Independent research reaches the same verdict on policy difficulty. An agent-sandbox reviewer found a profile that "failed to properly block off access to the user's home directory dotfiles and `~/Library`" and noted such mistakes are "easy to make with Seatbelt but harder to make with containers" ([quoted in Pierce Freeman, "A deep dive on agent sandboxes"](https://pierce.dev/notes/a-deep-dive-on-agent-sandboxes), CITED). A published walkthrough of a commercial agent's allow-default profile reached unsandboxed code execution via a `devfs` mount and a Launch Services handoff, bypassing provenance xattrs with symlinks ([Pillar Security](https://www.pillar.security/blog/escaping-antigravitys-allow-default-seatbelt), CITED; underlying Apple bug [CVE-2023-32364](https://gergelykalman.com/CVE-2023-32364-a-macOS-sandbox-escape-by-mounting.html)). In fairness, that chain **did not reproduce** under `(deny default)` in our testing: `open` on an app built by the sandboxed process was refused with error −54 and the bundle carried `com.apple.provenance`, most likely because `deny default` blocks the `mount -t devfs` the chain depends on (MEASURED, this machine). The primitive is not the weak part. The authoring is.

The scale of that authoring burden is the best available proxy for grove's maintenance cost, and it is large. Anthropic's runtime is roughly 1,700 lines of TypeScript whose hard-won invariants include: emitting paths in **two spellings** (as written and resolved) so a deny covers alias and target; splitting literal-vs-glob **once, by who produced the spelling**, never re-derived from characters (a directory named `a[b/c]d` would otherwise compile to a character class and every deny would match nothing); a `file-read-metadata` escape hatch so `realpath()` can traverse denied regions; and a trailing `(deny file-write-unlink …)` block because any read-denied path inside a write root is otherwise **movable** — `mv .env x; cat x` defeats both glob and literal denies (all CITED from the runtime source, verified by direct fetch). Chromium's Mac Sandbox V2 exists to sandbox Chromium's *unsandboxed warmup phase*, and the stated benefit of enumerating resources explicitly is that "it is possible to accurately audit Chromium's attack surface for each new macOS version" — with an OWNERS review required for every new policy ([Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/sandbox/mac/seatbelt_sandbox_design.md), CITED). That is what grove would be signing up for: a profile that must be re-audited on every macOS release, forever.

Two operational facts make that concrete. First, profiles must be passed by file (`sandbox-exec -f`), not inline (`-p`): Claude Code hit `ARG_MAX` on a machine with many worktrees, breaking the sandbox entirely at **8–11 worktrees** (~75 KB of argv per worktree), with a base profile already over 256 KB ([anthropics/claude-code#73468](https://github.com/anthropics/claude-code/issues/73468), CITED, verified fixed upstream). `sandbox-exec` additionally rejects any string literal over 1,025 bytes, so the runtime caps its own generated regexes at 900 bytes because "one oversized string invalidates the whole profile". Second, and not a cost grove can engineer away: **`sandbox-exec` is deprecated.** `man sandbox-exec` on this machine reads "The `sandbox-exec` command is DEPRECATED. Developers who wish to sandbox an app should instead adopt the App Sandbox feature" (MEASURED, this machine; page dated 2017). Apple has been asked directly what replaces it and **has not answered** — the issue is assigned to an Apple engineer and remains open, with the reporter noting that `sandbox-exec(1)` "is the only documented mechanism for applying Seatbelt… to arbitrary user-space processes on macOS without enrolling in the App Store or using Xcode entitlements" ([apple/containerization#737](https://github.com/apple/containerization/issues/737), CITED, re-fetched 2026-10-10). No removal timeline exists and none should be asserted. The honest reading is that Apple is deprecating the *public surface* while keeping the *mechanism* — 510 Apple base profiles still ship on disk (MEASURED, this machine) — but grove would be building on an interface its vendor has publicly been asked to replace and has declined to commit either way on.

## What remains unknown, and what it would cost either way

Listed honestly, with the cheapest experiment first. **Nobody has benchmarked `sandbox-exec` overhead on a real build workload** — my microbenchmark closes part of this (no measurable I/O cost at 2,000 iterations) but not the question; the cheapest decisive test is `sandbox-exec -f <profile> /usr/bin/time <a real `cargo test` / `npm run build`>` against the same run unconfined, on one real grove session's command set. **grove's actual inherited-FD exposure through the Electron → tmux-server → pane chain is unmeasured** and is the single most decision-relevant unknown; it is closed by having a pane run `ls -l /dev/fd` and a write-through probe before and after a proposed `sandbox-exec` boundary is inserted. **Whether a tightened profile survives a real interactive agent TUI** — MCP servers, background daemons, notifications, keychain prompts, TUI redraw — is unmeasured; every probe so far used short-lived CLI commands. **Whether a profile stays comprehensible for N session roots** is unmeasured. And there is no basis at all, public or private, for comparing how often real-world escapes occur under each approach — the security comparison rests on mechanism (shared kernel and hand-authored policy vs. separate kernel and enumerated mount set), not on incident rates (INFERRED).

The cost of each direction is concrete. **Staying with Apple `container` costs** one-VM-per-container resource cost measured nowhere, and no Compose support as of the last release grove evaluated. It does **not** cost a mount fault: that fault was a misdiagnosis of our own testing and is retracted above. What it buys is a separate kernel, a mount table whose mistakes are loud, native tree-wide inheritance without descriptor caveats, and credentials that are absent rather than merely denied. **Switching to Seatbelt costs** a security-posture downgrade against an actively adversarial agent, a new permanent maintenance obligation (per-release profile re-audit), a dependency Apple has marked deprecated with no successor, silent rule-ordering failures that our own researchers documented backwards, and the loss of the container's clean answer to the FD-inheritance problem. It buys the elimination of two whole subsystems, ~6 ms startup, native binaries with no image, a real egress deny-all primitive that ADR 0036 says is missing, and — uniquely among all the options surveyed — working Keychain control.

## Conclusion

The most consequential thing this research produced is not a recommendation but a correction to the premise: **the ENODEV failure that appeared to block ADR 0034 was never real.** `container run -i -t` requires a controlling TTY; every "mount failure" we recorded carried that flag; and from a PTY the design's whole argv works, including a real `git commit` inside a sandboxed worktree that the host then saw. That removes any urgency from the mechanism question.

The second-order lesson is about our own process, and it is the same lesson twice over. Two of four researchers independently documented Seatbelt's rule ordering backwards — it is **last-match-wins** — and building to their combined guidance would have produced a profile that silently leaked every path it was meant to protect. Then the report itself arrived with a confident "MEASURED" claim that the blocker had cleared; the coordinator retracted it; the coordinator's own replacement claim was also wrong; and the actual truth turned out to be that *neither* was right. Where a primary source is readable it must beat a note's interpretation, and where researchers conflict the conflict is itself the finding. Most of all: **a measurement taken in a context that does not match the runtime is worse than no measurement**, because it arrives wearing a confidence label it has not earned. We tested from a shell with no TTY; grove runs inside a tmux pane.

So the question this research was commissioned to answer turns out to be answerable, but not urgently: **ADR 0034's container approach works as designed on this machine, and there is no forced reason to change mechanism.** If grove were to move to Seatbelt anyway, the trade would be a considered one — a permanent security-posture downgrade and a permanent profile-audit burden, bought in exchange for deleting the image subsystem and the OpenCode bridge, gaining native binaries and Keychain control. That is a real decision worth taking deliberately. It is not one worth taking because a terminal looked red.

If the container path does prove unusable on this machine, Seatbelt is a defensible **engineering** choice for grove and a poor **security** one, and the difference between those two framings is the whole decision. grove's stated promise is that an agent may roam its working directory but is *structurally unable* to touch the rest of the host; under Seatbelt "structurally" becomes "by policy, as long as the policy is correct, the paths compile, and no inherited descriptor was handed down by tmux." Under a container it means "because of what exists inside the jail." For a misbehaving agent those are nearly equivalent. For a prompt-injected one actively hunting for holes, they are not — and grove would be choosing to own that gap explicitly rather than inheriting it from a VM. Changing the mechanism remains a design revision for a human to decide; nothing in `docs/adr/` or `docs/work/2026-10-08-agent-sandboxing/` has been modified by this research.

## Correction note (added by the coordinator, then corrected again)

This report has been wrong about the central fact twice, and both errors are recorded here rather than quietly fixed.

**First error.** An early version opened by claiming the ENODEV mount failure "did not reproduce" on the maintainer's machine, reporting successful bind mounts, `--tmpfs` and `--read-only-path` at a 0.76 s warm start. That was false, and the coordinator retracted it.

**Second error — and the actual truth.** The coordinator then reported the opposite: that the fault was *still active*, on the basis of re-measurement. **That was also wrong, and so was the original investigation underneath it.** The fault is not a mount fault at all.

Measured 2026-10-11 on macOS 26.4.1 (25E253), `container` 1.5.0:

| Run | non-TTY shell | real PTY / tmux pane |
| --- | --- | --- |
| `container run --rm alpine true` | pass | pass |
| `container run --rm -i alpine true` | pass | — |
| `container run --rm -t alpine true` | pass | — |
| `container run --rm -i -t alpine true` | **ENODEV** | **pass** (`/dev/pts/0` allocated) |
| `container run --rm -i -t --volume … alpine …` | **ENODEV** | **pass** (volume contents listed) |

`container run -i -t` requires a real controlling TTY on the host. Every 2026-10-10 "mount" failure carried `-i -t`, which is why mount-only runs (`--tmpfs`, `--read-only-path`) appeared to fail too — they were run with `-i -t` and failed for that reason. **The mount subsystem was never broken.** The reboot changed nothing about this; what changed is that the diagnosis was wrong.

The upstream issue cited earlier, [apple/container#1254](https://github.com/apple/container/issues/1254), was also a red herring: it describes `VZErrorDomain Code=1 "The virtual machine failed to start"` — the VM never boots. Here the VM boots fine. That citation should be disregarded as a diagnosis.

Confirmed working end to end in a real tmux pane, using the design's prescribed argv (host-identical volumes for the worktree and the git common dir, nested read-only carve-outs for `hooks/` and `config`, an absent `--read-only-path` target, `--tmpfs`, the three `GIT_CONFIG_*` variables): `git rev-parse --show-toplevel` and `--git-common-dir` resolved correctly, `core.hooksPath` returned `/dev/null` with the host's `post-commit` hook not running, and **a real `git commit` executed inside the container with the host then seeing the advanced worktree HEAD and the agent-written file**. The main checkout stayed clean. Warm `container run` ≈ 0.7 s.

The root cause of both errors is worth stating plainly, because it is the same shape as the error this report already flagged in its own research notes: **we tested in a context that did not match the runtime.** grove runs its leaf command inside a tmux pane; every test here ran from a shell with no TTY on stdin. A measurement taken in the wrong context is worse than no measurement, because it comes with a confident label attached.

Consequently **nothing in this report's Seatbelt analysis changes**, and the recommendation it reaches is unaffected: Seatbelt is defensible as engineering and weak as security, and the case for making that trade is now a considered design decision rather than an emergency response to a broken host. What the investigation *does* change is urgency — there is no longer a forced move. ADR 0034 remains a sound basis for slice 1, and the open `grove ls` question is the only thing actually blocking it.
